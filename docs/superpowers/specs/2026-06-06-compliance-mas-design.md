## 1. Контекст и мотивация

### Что было

Исходный план `regulatory-mas-agent` (README/PLAN.md от 2026-06-05) описывал обобщённый MAS поверх SIA RAG через MCP: Coordinator → RegulationsAgent/WebAgent/CalcAgent → synthesize → CriticAgent. Прожарка плана вскрыла:

- `mcp_server.py` в SIA **не существует** — весь MCP-слой был фикцией.
- RegulationsAgent оборачивал SIA, который **сам уже является агентным графом** (router/triage/abstain/rerank) — value-add не сформулирован.
- CalcAgent через `eval()` — RCE и надуманный сценарий.
- Бенчмарк «MAS vs baseline SIA» на `dataset_original.csv` предрешён: SIA тюнили 80 сессий на этом датасете.
- Главный вопрос «зачем MAS, если SIA отвечает за 10с» — без ответа.

### Ключевая находка

Комплаенс-MAS **уже существует** — в виде Claude Code скиллов:
- `process-doc` (скилл) = координатор (конвертация → параллельный запуск агентов → консолидация).
- `check-regulations` (агент) = проверка актуальности НПА (web: pravo.gov.ru, garant).
- `doc-validator` (агент) = содержательная проверка требований (периодичность, формы, сроки).

Это буквально coordinator → specialists → synthesize. Пётр пользуется им в реальной работе по ОТ/ПБ.

### Решение о цели (мотив A+B)

Не «обёртка ради демо», а **перенос проверенного пайплайна в автономный LangGraph-продукт**:
- **A — автономный инструмент.** Claude Code агенты живут только внутри Claude. LangGraph-версия деплоится (Streamlit/API), её можно дать коллеге по ОТ, встроить в рабочий процесс без Claude.
- **B — карьерный артефакт.** Закрывает зафиксированный после интервью Сбера (03.06.2026) пробел: «нужен агентный проект с tool calling поверх SIA». На интервью «MAS на LangGraph + tool calling + eval» сильнее, чем набор конфигов харнесса.

Польза уже доказана (Пётр использует Claude Code версию); LangGraph-версия делает её автономной и измеримой.

## 2. Цель и критерии успеха

**Цель:** задеплоиваемый LangGraph multi-agent, который принимает нормативный документ организации и возвращает отчёт о несоответствиях действующим НПА, с привязкой каждого вывода к источнику.

**Критерии успеха MVP:**
1. На тестовой инструкции СПЗ граф **воспроизводит находки эталонного** `check_regulations_report.md` (recall НПА ≥ эталона).
2. Каждый вывод имеет источник (провенанс) — 100%, гейтится Critic.
3. Корректно ловит реальные кейсы из проекта `pb`: СП 9.13130.2009 → ❌ утратил силу; ГОСТ Р 59641 Изм.1 → ⚠️; ПП 1479 ред. ПП 90 → актуальная.
4. Деплоится как сервис (Streamlit), работает без запущенного Claude Code.

**Не является критерием:** превзойти SIA по correctness на его датасете (другой класс задачи — комплаенс-чек документа, не Q&A).

## 3. Scope

### MVP (эта спека)
- Вход: один тип документа — **инструкция** (тестовый кейс: инструкция по содержанию средств ПЗ, проект `pb`).
- Режим: **DETECT** — обнаружение несоответствий + отчёт. Без авто-правок.
- Каскад источников: SIA (корпус) → web (Tavily, с пометкой надёжности) → ❓.
- Провенанс на каждом выводе.
- Деплой: Streamlit + CLI.

### Фаза 1.5 (следующий шаг после надёжного detect)
- **FIX** — генерация предложенных правок (proposed_edits): якорь → было/стало → обоснование + ссылка на норму + источник.
- **human_review** — LangGraph `interrupt()` для одобрения каждой правки (паттерн `book_flight→interrupt→approval` из лекции 2).
- **Checkpointer** (SqliteSaver) — технический фундамент `interrupt()` (без него граф не паузится). Появляется здесь вместе с fix/human-review, в detect-only MVP не нужен.

### Фаза 2 (отложено, ценно)
- MCP-обёртка SIA (REST → MCP) — «начал с REST, обернул в MCP».
- Long-term memory — профили организаций + ChromaDB история запросов.
- Iron User для eval review-петли (симулятор спеца ОТ, принимающего правки).
- Расширение корпуса SIA — добавить СП по пожарке (484/486/3.13130), растит покрытие каскада.
- Новые типы документов — положения о СУОТ, программы обучения, акты.

### Out of scope (решили не делать, с обоснованием)
- **HyDE** — SIA уже имеет `query_expand` внутри; HyDE на стороне MAS дублировал бы.
- **CalcAgent через `eval()`** — RCE + надуманный сценарий для домена НПА.
- **Динамический Coordinator-планировщик** — поток комплаенс-чека детерминирован (шаги известны заранее), LLM-планировщик избыточен (тот же грех, что CalcAgent ради галочки).

## 4. Архитектура

LangGraph `StateGraph`. Поток детерминирован (не динамический план).

### Состояние
```
ComplianceState (TypedDict):
  document: str               # текст документа
  doc_meta: dict              # тип, название, организация
  npa_list: list[NPA]         # извлечённые ссылки на НПА
  requirements: list[Req]     # извлечённые проверяемые требования
  findings: Annotated[list[Finding], add]   # reducer — копится от параллельных узлов
  report: str | None
  # фаза 1.5: proposed_edits, review_decisions
```

### Узлы
1. **input_guard** — валидация входа: это нормативный документ, а не случайный файл? (лек.2, адаптирован). Дёшево, отсекает мусор. off → END с сообщением.
2. **extract** — LLM извлекает: (а) НПА из раздела «Нормативные документы» + инлайн-ссылки («п.50 Правил ПР»); (б) проверяемые требования (периодичность, значения, формы). Структурированный вывод (Pydantic schemas).
3. **Специалисты (fan-out, параллельно):**
   - `npa_validator` (перенос логики `check-regulations`) — актуальность каждого НПА.
   - `requirement_validator` (перенос логики `doc-validator`) — содержательная актуальность требований.
   - `sia_crosscheck` — точный текст нормы из корпуса SIA + (фаза 1.5: visual_proof).
4. **synthesize** — собирает `findings` в отчёт (формат `check_regulations_report.md`).
5. **critic** — гейт качества отчёта: у каждого ли finding есть источник, не выдумал ли synthesize вывод без провенанса (Reflexion над своим выходом, лек.3). НЕ дубль abstain SIA. При провале — возврат на synthesize.
6. **(фаза 1.5)** `human_review` — interrupt для одобрения правок.

### Каскад доверия (ядро ценности)
На каждый проверяемый факт:
1. **SIA** (если норма в корпусе: ПП 1479, 69-ФЗ) — приоритетный источник: точный текст + (1.5: visual_proof).
2. **Web/Tavily** (где SIA пусто) — с явной пометкой «источник web, надёжность ниже».
3. **Ни там, ни там → ❓ «не проверено»** — не выдумываем.

Каждый вывод привязан к источнику. Это и продукту даёт честность (критично для compliance), и портфолио — provenance/trust.

### Поток на реальном документе (инструкция СПЗ)
- ПП 1479 → есть в корпусе SIA → точный текст пункта ✅ (приоритет).
- ГОСТ Р 59641-2021 → нет в SIA → web → Изм.1 от 01.10.2024 ⚠️.
- СП 9.13130.2009 → web → утратил силу 01.03.2025 ❌ → заменён ГОСТ Р 59641 (реальный кейс из CLAUDE.md pb).

## 5. Интеграция с SIA (HTTP API)

Выбран вариант HTTP (из 3: HTTP / MCP / прямой импорт).

- SIA `api.py` уже имеет `POST /query` (rate-limit 10/min) + `GET /health` — мост готов в коде.
- `sia_tool` = `@tool`, делает `httpx`-запрос к SIA `/query`, возвращает `{answer, passages[], path}`.
- `visual_proof` через `/query` недоступен (endpoint отдаёт только текст/passages, не bbox/рендер) → отложен на фазу 1.5 (нужен отдельный SIA endpoint или MCP). В MVP `sia_crosscheck` использует текст пунктов из `passages`.
- SIA изолирован: свой venv, ChromaDB, WARP-прокси для Gemini остаются внутри SIA; MAS чист (мотив A — два деплоиваемых сервиса).
- **Операционно:** SIA сейчас не запущен (порты молчат, нет tmux `sia`). Поднять SIA API в tmux на 8503. Порт 8504 занят чужим streamlit — MAS дать свободный (уточнить при деплое).

Почему не MCP в MVP: писать FastMCP-обёртку в repo SIA с нуля = та же `/query` ради галочки. MCP → фаза 2 как осознанный апгрейд.

## 6. Выход

1. **Отчёт** (формат `check_regulations_report.md`):
   - Таблица: `| НПА | Статус ✅⚠️❌❓ | Источник (SIA/web) | Примечание |`
   - Содержательные находки по требованиям: цитата + статус + что изменилось + источник.
   - Раздел «Что учесть при обновлении».
2. **(фаза 1.5) Предложенные правки:** якорь (пункт) → было/стало → обоснование + ссылка на норму + источник → статус pending/approved/rejected.
3. Провенанс на каждом выводе — обязателен (Critic гейтит).

---

## 7. Eval (лекция 4)

- **Ground truth:** `check_regulations_report.md` (готовый эталон проверенного прогона). ⚠️ Покрывает только НПА (1 специалист из 3). Для `requirement_validator` и (1.5) правок — ручная разметка Петра.
- **Task basket:** тест-документы с известными проблемами. Старт — инструкция СПЗ. Размеченные кейсы из CLAUDE.md pb:
  - СП 9.13130.2009 → ❌ утратил силу
  - ГОСТ Р 59641 Изм.1 → ⚠️
  - ПП 1479 ред. ПП 90 → актуальная
- **Graders:**
  - deterministic — recall НПА (нашёл ли все из эталона), совпадение статусов.
  - LLM-as-Judge (gpt-4o) — качество находок/правок, отсутствие галлюцинаций.
  - провенанс — % выводов с источником (цель 100%).
- **Baseline сравнения:** Claude Code прогон (`process-doc`). Показать, что граф воспроизводит/обгоняет.

## 8. Стек и структура проекта

**Стек:** LangGraph, langchain-openai (gpt-4o-mini агенты + gpt-4o critic/judge), Tavily (web), httpx (SIA), Pydantic (границы), structlog, pytest. SqliteSaver — фаза 1.5.

**Структура** (текущие README/PLAN.md завязаны на старую MCP-архитектуру — переписать в реализации):
```
regulatory-mas-agent/
├── agent/
│   ├── state.py        # ComplianceState (TypedDict + reducers), Pydantic schemas
│   ├── guards.py       # input_guard
│   ├── extract.py      # узел извлечения НПА + требований
│   ├── tools.py        # sia_tool (httpx /query), web_tool (Tavily)
│   ├── specialists.py  # npa_validator, requirement_validator, sia_crosscheck
│   ├── synthesize.py   # отчёт
│   ├── critic.py       # провенанс-гейт
│   └── graph.py        # сборка StateGraph
├── eval/
│   ├── task_basket.py  # тест-документы + эталоны
│   ├── graders.py      # deterministic + LLM-judge + провенанс
│   └── run_eval.py
├── app.py              # Streamlit (загрузка → отчёт)
├── main.py             # CLI
└── tests/
```

## 9. Обработка ошибок

- SIA недоступен → graceful fallback на web с пометкой, не падаем.
- Web пусто/ошибка → ❓ «не проверено».
- Никогда не выдумываем факт без источника (Critic гейтит).
- `httpx` к SIA — таймаут + явная обработка (no bare except).

## 11. Риски (приняты осознанно)

1. **Покрытие SIA на пожарной инструкции скромное.** Из ~4 НПА в корпусе SIA только ПП 1479 и 69-ФЗ; ГОСТ 59641 и СП 3.13130 → web (ненадёжный). SIA-преимущество видно на 1-2 пунктах из 4. Сильнее проявится на документах по ОТ (корпус богаче) или после расширения корпуса (фаза 2). Для MVP ожидания трезвые; честно покажем границы каскада.
2. **Extract — самый хрупкий узел.** Пропустит требование → никто его не проверит (тихий recall-риск). Митигация: отдельный eval на extract.
3. **Эталон частичный** — только НПА. Для требований и правок нужна ручная разметка (время Петра).
4. **Fix (фаза 1.5) рискован** — генерация правок юридического текста чревата галлюцинациями. Митигация: human_review (interrupt) + провенанс.

## 12. Порядок реализации

**Walking skeleton первым** (не строить 7 узлов сразу):
1. Тонкий вертикальный срез: `extract → npa_validator (каскад SIA→web) → synthesize → CLI-отчёт`. Цель — воспроизвести находки эталона по НПА.
2. Добавить `requirement_validator` + `sia_crosscheck` (fan-out).
3. Добавить `critic` (провенанс-гейт) + `input_guard`.
4. Eval (task basket + graders), сверка с baseline.
5. Streamlit UI.
6. Деплой (SIA API в tmux + MAS Streamlit).

Фаза 1.5 (fix + human_review + checkpointer) — после надёжного detect.
